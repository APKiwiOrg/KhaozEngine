# KhaozEngine

A shared, game-agnostic, **MonoGame-free** 2D/3D engine: windowing + input, a GPU abstraction, 2D and 3D
renderers, an immediate-mode + screen-stack GUI, audio, particles, an ECS, netcode, and the usual foundation
(content, persistence, localization, diagnostics). One implementation, used by four games (Hardpoint,
Nullwake, SpaceGame, Ruinborne), so a fix written once propagates to all of them.

KhaozEngine is split into focused, independently-referenceable NuGet packages plus a few umbrella metapackages,
so a game pulls in just what it needs (and a logic library or headless server can pull a renderer-free subset).

| **KhaozEngine.Gpu.D3D11** | The engine's own native Direct3D 11 backend for the `KhaozEngine.Gpu` seam (opt-in, NOT in any umbrella, added explicitly like `Physics.Bepu`). One public entry point, `KhaozEngineD3D11.Register()`, registers an `IGpuBackendProvider` for `GpuBackendKind.Direct3D11Native`, so opting in is a package reference plus one line at startup rather than a `[ModuleInitializer]` the CLR may never run (a missing registration then throws naming that line instead of silently falling back onto a different backend and filing a soak session's numbers under the wrong name). Targets `net10.0`, deliberately not `net10.0-windows`: the Windows boundary is `[SupportedOSPlatformGuard("windows")]` entry points over `NoInlining` Vortice bodies, so the assembly compiles and its device-free tests run on Linux and macOS while the Vortice interop stays off the load path there, and CA1416 enforces the boundary at compile time. The machine-capability probe behind `IsBackendSupported` creates a throwaway feature level 11_0 device (hardware, then WARP) and checks the two hard device requirements the backend cannot work without, `ConstantBufferOffsetting` and `MapNoOverwriteOnDynamicConstantBuffer`, so an incapable machine is reported and falls back rather than crashing on the first frame. Carries no `Veldrid` edge of its own (asserted on both the project graph and the built IL): the SPIRV-Cross shader path stays in `KhaozEngine.Gpu` behind an internal, Veldrid-free cross-compile helper. Diagnostics: `KE_D3D11_ADAPTER=warp|hardware|<index>|<name substring>` pins which adapter the device is created on (an unhonourable request WARNs, lists what WAS enumerated, and falls back to letting DXGI pick, never fails), `KE_D3D11_DEBUG=1` adds `D3D11_CREATE_DEVICE_DEBUG` and pumps `ID3D11InfoQueue` into the engine log rate-limited with corruption and error raised to WARN, and a device loss calls `GetDeviceRemovedReason` at the first site that notices, latches it, flips the liveness token and surfaces it in the telemetry session header alongside the software-adapter flag. Capabilities are at parity with the incumbent field for field, `SupportsCompletionFences` excepted, with an out-of-range MSAA request throwing at texture creation rather than silently degrading. **Device creation is real**, so `CreateForWindow` and `CreateHeadless` build a device on Windows and everything above is reachable, but **nothing selects this backend by default**: it is reached only by naming it (`KE_GRAPHICS_BACKEND=direct3d11-native`, or an explicit `GpuBackendKind.Direct3D11Native`). The `direct3d11-native` CI leg exists now and is blocking, verifying the shared `direct3d11` goldens on a pinned WARP adapter, and its first recorded evidence is rollout gate 1 on https://github.com/APKiwiOrg/KhaozEngine/issues/460, which is also where the five rollout gates decide the default flip. `KhaozEngine.Gpu`'s `Direct3D11` backend stays the working one and stays selectable indefinitely. | Gpu, Diagnostics (+ Vortice) |
| **KhaozEngine.Gpu.Vulkan** | The engine's own native Vulkan backend for the `KhaozEngine.Gpu` seam (opt-in, NOT in any umbrella, added explicitly like `Physics.Bepu`), and phase 3 of the staged native GPU backend program. **REGISTRATION, PROBE, A HEADLESS DEVICE, ITS COMPLETION TIMELINE, ITS MEMORY ALLOCATOR, THE COMMAND LIST'S LIFECYCLE, THE UNIFORM RING, THE RESOURCE FACTORY, THE DESCRIPTORS, THE BIND FLUSH, DYNAMIC RENDERING, THE SHADER PATH, THE PIPELINES, THE WINDOWED SWAPCHAIN, THE BARRIER TRACKER, THE CAPABILITY, COUNTER AND DIAGNOSTICS READS AND THE DRAW, DISPATCH AND TRANSFER PATHS as of 17.34.0**: `KhaozEngineVulkan.Register()` registers a real provider, that provider answers a real functional machine probe (a Vulkan loader, a throwaway instance at the 1.3 floor, every physical device read against the design's requirements, and the instance destroyed before the answer returns), and `GpuDeviceContext.CreateHeadless(GpuBackendKind.VulkanNative)` builds a real `VkDevice` and graphics queue on one refcounted process `VkInstance`, with features enabled by name, a device-loss latch that fires in Release and the `KE_VULKAN_DEVICE` / `KE_VULKAN_VALIDATION` levers ([#514](https://github.com/APKiwiOrg/KhaozEngine/issues/514)). That device owns ONE timeline semaphore with a real `IGpuFence`, a counted `vkWaitSemaphores` drain and the deferred-disposal retire list ([#515](https://github.com/APKiwiOrg/KhaozEngine/issues/515)), plus an engine-owned block suballocator ([#516](https://github.com/APKiwiOrg/KhaozEngine/issues/516)): chunks pooled by `(memoryTypeIndex, linear|optimal)` so `bufferImageGranularity` is satisfied by separation rather than by the incumbent's per-allocation rounding, first-fit with alignment correction and coalescing free, host-visible chunks mapped once at creation and never unmapped, dedicated allocations on driver preference or above a size threshold, and real flush and invalidate on the non-coherent path that the incumbent has nowhere at all. It also hands out real command lists ([#517](https://github.com/APKiwiOrg/KhaozEngine/issues/517)): `FramesInFlight` `VkCommandPool`s per list reset with `vkResetCommandPool` rather than the incumbent's one pool with `RESET_COMMAND_BUFFER`, a slot wait counted as backpressure through `KE_VULKAN_FRAMES_IN_FLIGHT`, pools handed to the retire list when a list is disposed in flight, and `Submit` as ONE `vkQueueSubmit` whose timeline value is allocated inside the lock that orders it, with a failed submit registering nothing so the drain can never be left waiting for a value nothing will signal. There is no CPU op stream and no second recording driver, which is a decision rather than a gap: a `VkCommandBuffer` already IS the deferral the Direct3D 11 recorder had to build. It owns the UNIFORM RING too ([#518](https://github.com/APKiwiOrg/KhaozEngine/issues/518)): every `UniformBuffer`-usage buffer is ONE `VkBuffer` of `stride * FramesInFlight` in host-visible coherent persistently mapped memory, with the per-frame base applied at BIND so the `IGpuBuffer` identity never changes, a segment recycled against the timeline's COMPLETED value rather than a submit receipt, and a record-time `UpdateBuffer` that is a `memcpy` with no staging buffer, no copy command, no barrier and no render-pass split (the shipped incumbent's same call is a render-pass split plus a full pipeline flush plus a global barrier whose destination mask does not even cover a uniform read). A device-level `UpdateBuffer` reaches EVERY segment and NEVER BLOCKS, deferring a segment still in flight as a pending patch the next frame boundary replays, which is [#484](https://github.com/APKiwiOrg/KhaozEngine/issues/484)'s correction adopted wholesale. **One backend divergence lands with it and is documented rather than discovered: a buffer created `UniformBuffer` combined with any other bindable usage is REFUSED at creation, where `GpuBackendKind.Vulkan` accepts it.** Bulk payloads take a per-list staging arena instead, pooled by size class with a real 8 MiB retention cap against the incumbent's 512 bytes, with the copy barrier narrowed to the destination's actual usage. The ring's SEMANTIC policy is tested against BOTH backends' rings through one internal test-only interface in `KhaozEngine.TestSupport.Gpu`, which is what the decision to share the tests rather than the code owes. It has a REAL RESOURCE FACTORY too ([#519](https://github.com/APKiwiOrg/KhaozEngine/issues/519)): every `VkImageView` is created at RESOURCE creation from the declared usage bits and none at a bind or a draw, with no view factory reachable from the recording type at all, because all 25 `DEVICE_REMOVED` stacks in [#423](https://github.com/APKiwiOrg/KhaozEngine/issues/423) surfaced inside a lazy view constructor on the draw path and no counting seam can see a `vkCreateImageView`. Every texture is assigned its canonical RESTING LAYOUT at creation, which is what lets lists compose in any submit order. NO texture creation submits anything: the incumbent issues a whole `vkQueueSubmit` per render target and per sampled texture created, so two hundred textures is two hundred submissions before a frame is drawn, and here the clear and the first-ever transition are appended to ONE device-owned setup command buffer under its own short lock, flushed at the next submit or at any device-level read. The clear is preserved deliberately, because undefined contents are not stable across runs. Staging is a `VkBuffer` with the incumbent's SOFTWARE subresource layout reproduced byte for byte and pinned by a checked-in 63-row table taken from the incumbent's own arithmetic, because every golden reads back through `Map` and `MappedData.RowPitch` and a different arithmetic garbles all 36 at once. `Map(staging, Read)` waits on the timeline's last submitted value first, counted as a drain, which is the thing Direct3D 11's `Map(READ)` did implicitly. The shared point and linear samplers WRAP on all three axes, built from wrap-addressed descriptions and NOT from the identically named `GpuSamplerDescription` statics, which default every axis to clamp and cost two goldens on the Direct3D 11 leg. Disposal is one TERMINAL retire per resource, destroying children inline rather than re-retiring them, which bounds the retirement depth at the generation the teardown already drains twice for. **A second documented divergence lands with it: `GpuBufferUsage.Dynamic` does not make a buffer CPU-mappable there, where it does on the Veldrid leg.** It has DESCRIPTORS too ([#520](https://github.com/APKiwiOrg/KhaozEngine/issues/520)): `VkDescriptorSetLayout` and `VkPipelineLayout` are CONTENT-DEDUPLICATED, which is not a micro-optimisation but the thing that makes bound descriptors survive a pipeline switch (Vulkan decides pipeline-layout compatibility by comparing set layouts, so one handle per distinct content turns that into a pointer compare, where the incumbent creates one per `ResourceLayout` object and therefore makes nothing ever compatible with anything). Every uniform buffer binds as `UNIFORM_BUFFER_DYNAMIC` rather than only the elements declared dynamic, because the per-frame ring base has to be applied at bind and the dynamic offset is the only bind-time knob Vulkan offers on a uniform buffer, so the declared flag decides exactly one thing: whether the caller's own per-draw offset is added on top. Pools are sized from ACTUAL demand rather than the incumbent's fixed `maxSets = 1000` with 100 descriptors of each of seven types, and freeing restores EVERY counted type: the incumbent's free path restores five and forgets `UniformBufferDynamicCount` and `StorageBufferDynamicCount`, so an application that churns dynamic-offset resource sets leaks pool budget forever, which is aimed squarely at a consumer whose sets are overwhelmingly dynamic-offset ones and whose map editor churns them on every document load. A set is allocated and written ONCE at creation with one `vkUpdateDescriptorSets` covering every binding, and the descriptor's range is the BIND WINDOW: never `VK_WHOLE_SIZE`, and never the ring stride, which is the shape that looks safe and overruns the buffer at the last frame slot by exactly the caller's own offset for the five shipped renderers that pass a non-zero one. Zero descriptor allocations and zero descriptor writes during recording is enforced STRUCTURALLY, because neither call is a bind, a draw or a barrier and no counting seam can ever see them: the pool is unreachable from the recording type. And a device-free test asserts every one of the 33 shipped pipeline shapes stays at or under Vulkan's required minimum of 8 dynamic uniform buffers, so a layout combination that would break a minimum-spec device fails on the free Linux leg rather than on a player's machine. Descriptor indexing, bindless, push constants and descriptor buffers are all declined with an argument rather than an omission, and the trigger that reopens them is named. All four resource-set BINDS are live too ([#521](https://github.com/APKiwiOrg/KhaozEngine/issues/521)): a bind RECORDS ONLY into a per-slot `(set, offset)` array with TWO dirty states rather than the Direct3D 11 backend's three, because a Vulkan descriptor bind is one call whether one offset moved or every image in the set changed, so a third state would change no call and skip no work. The flush emits ONE `vkCmdBindDescriptorSets` per CONTIGUOUS RUN of dirty slots with `firstSet` at the run's start, so a full activation is one call carrying every set and an offsets-only rebind is one call carrying one, which is the whole Vulkan argument for the descriptor model and a number a budget ported from the other backend could not even express. `pDynamicOffsets` is POSITIONAL and covers sets the caller never named: one entry per dynamic descriptor in the run, in set-then-binding order, each composed as `ringBase + rangeOffset + (declaredDynamic ? engineOffset : 0)`, recomposed once per run rather than accumulated across a flush, which is the incumbent's own defect (it resets the batch count and the first set but not the offset count, so a second batch passes a too-large count built from stale entries) not being inherited. A device-free test composes the array for all 33 shipped layout shapes at every frame slot and asserts each entry plus the descriptor's range stays inside the buffer, which is the offset `VUID-vkCmdBindDescriptorSets-pDescriptorSets-01979` measures. Each entry is also checked at the flush against the ring's derived alignment (`VUID-vkCmdBindDescriptorSets-pDynamicOffsets-01971`), refused by name with the slot left dirty. A pipeline switch invalidates recorded slots from the first INCOMPATIBLE set onward, computed as the longest common prefix of the two pipeline layouts' set-layout handle sequences, which content dedup is what makes both correct and cheap. That prefix is GUARDED rather than trusted, because a prefix longer than the truth leaves a set the driver invalidated marked clean and the next draw renders wrong without throwing: a device-free test walks all 1089 ordered pairs of the 33 shipped pipelines and asserts the computed prefix never exceeds the true prefix of identically DEFINED set layouts (compared by binding table, not by handle, so the guard is not a restatement), and under `KE_VULKAN_VALIDATION` the flush asserts every bound set's layout is the pipeline layout's set layout at that index. It has DYNAMIC RENDERING too ([#522](https://github.com/APKiwiOrg/KhaozEngine/issues/522)), and the headline there is an absence: there is no `VkRenderPass` and no `VkFramebuffer` anywhere in the backend, so no cache for either and no invalidation of either on a resize, against an incumbent that creates three passes per framebuffer with no cache, dedups nothing across framebuffers of identical format, and rebuilds all of it every resize. `CreateFramebuffer` therefore makes no driver object at all and its disposal releases nothing, because every attachment view already exists on the texture. `vkCmdBeginRendering` is DEFERRED to the first draw, so a clear recorded after `SetFramebuffer` folds into `loadOp = CLEAR` instead of costing a `vkCmdClearAttachments`, while a clear arriving after the pass opened still issues one. `storeOp` is `STORE` unconditionally and `DONT_CARE` is not expressible, because undefined contents are not stable across runs and the goldens require stability on the same rasterizer. The clear-only pass is reproduced deliberately: a bind plus a clear plus an `End` with no draw still clears, through a begin and end pair, flushed at `End` and at the next framebuffer change, and it needs no did-a-draw-happen flag because a begin CONSUMES the pending clears. Every command illegal inside a render pass instance ends it first, through one helper with one device-free test. `SetFramebuffer` emits a viewport and a scissor ON A CHANGE ONLY, reproducing Veldrid's own identity guard whole: a backend that does not emit rasterises nothing, and one that emits unconditionally silently restores the full scissor over a live one on the shipped bind-scissor-draw-rebind-draw sequence, which is golden-visible. That viewport carries NEGATIVE height, which is what makes Vulkan's clip space match Direct3D's and why `ClipSpaceYInverted` stays false and `GpuClip.Correct` stays the identity: getting it wrong does not throw, it renders every golden upside down, so a device-free test asserts the emitted height alongside the goldens and the capability parity test. The rendering class got its OWN device-free seam rather than widening the budget seam, because nothing about a begin, an end, a viewport or a clear scales with draw count and freezing marginals over them would gate on figures nobody should gate on. It has a SHADER PATH too ([#526](https://github.com/APKiwiOrg/KhaozEngine/issues/526)), and it is the shortest one in the engine because there is no cross-compilation on it at all: Vulkan consumes SPIR-V, so each GLSL 450 source goes through the engine's own front end and `vkCreateShaderModule` takes the bytes verbatim, with no HLSL, no FXC, no register scheme to invent and no reflection read back off the module. `SpirvCrossCompile` was SPLIT along the seam it already had, into a glslang front end this backend depends on and a SPIRV-Cross back end it names no member of, asserted over the built IL because both halves live in `KhaozEngine.Gpu` and every other scan reads identically either way. That split is the whole Metal-facing carrying cost of the phase and it makes the eventual direct-SPIRV-Cross migration ([#462](https://github.com/APKiwiOrg/KhaozEngine/issues/462)) a change to one half of one file. The claim that the native backend hands `vkCreateShaderModule` the SAME bytes the incumbent does is TWO artefacts rather than one: a `SpirvFrontEndPin` stating the options as constants with a derived cache identity, and a one-off in-process measurement, taken 2026-08-08 before the first golden run, that compiled all 34 shipped graphics programs and all 8 compute kernels through both paths and found 76 of 76 stages byte-identical, which is what licenses the committed `vulkan` goldens carrying over without a rebake. The per-program hash table shipped alongside is a DRIFT detector and its header says so, because a wrong emission baked once passes forever. `VkShaderModule`s are deduplicated by SPIR-V hash within a device, so those 76 stage emissions are 59 distinct modules and `IGpuShaderSet.Dispose` releases nothing. And the `set` and `binding` numbers, which Vulkan inherits from the shared GLSL rather than inventing, get a device-free table test over every shipped program: N indexes the pipeline's layout array and M the layout's element array, and `SpriteBatch` declares its UBO at `set = 1`, so "the UBO set comes first" is false in shipped code and a reordered layout array would be caught by nothing else. It has PIPELINES too ([#523](https://github.com/APKiwiOrg/KhaozEngine/issues/523)), which close the resource factory's refusal list entirely: a pipeline create-info here names no `VkRenderPass` and no meaningful subpass, because the target's colour formats and depth format ride a `VkPipelineRenderingCreateInfo` built off the seam's own `GpuOutputDescription`, which is the whole of what a render pass would have carried and is why there is no pass to cache and nothing to invalidate on a resize (the same description's sample count rides the multisample state instead, since the rendering create-info has no sample-count field). Vertex input comes from the caller's own `GpuVertexLayoutDescription` list with no reflection read off the module, numbered as ONE flat location sequence across every buffer slot (restarting per slot reads the instance stream's first attribute as the vertex buffer's second, which renders plausible garbage rather than throwing) and packed within each, with a declared stride winning over the computed one. An instance step rate above 1 is refused by name, because Vulkan's core input rate is two-valued with no divisor and flattening a 2 to a 1 would draw every instance from the same element silently. Dynamic state is exactly viewport and scissor, expressed as a value a device-free test reads rather than a line inside a create-info no headless test can see, so everything else including the constant blend colour is baked into the pipeline object. **A blend state count that is not the colour output count is REFUSED by name, in both directions**, because Vulkan requires the two to be equal, the seam lets them differ with nothing checking, and a mismatch is a validation error at creation on a shipped renderer. Repairing it would invent a per-backend semantic for an attachment nobody described, where the Direct3D 11 native backend answers the same description with its own struct defaults, and `GpuPipelineDescription.BlendAttachments` is already documented as one per colour output with all 22 shipped call sites declaring exactly that. The `VkPipelineCache` is PERSISTED, against an incumbent that passes `VkPipelineCache.Null` at both creation sites and therefore recompiles every pipeline from SPIR-V on every launch across considerably more permutations than programs: one cache is created with the device, keyed on `(pipelineCacheUUID, driverVersion, engine version)` where the UUID is the vendor's OWN validity key, header-validated before `pCacheData` is ever passed, written back through a process-unique temp-and-move so a reader sees a whole entry or none, and best-effort at every step so a missing, unreadable, truncated or foreign file is a colder start rather than a throw. A driver that refuses a blob this backend accepted gets one retry with no seed AND the refused file deleted, which takes both: the retry rescues the run, and the delete is what stops the same rejected blob being read, seeded and refused once per launch after an unclean exit. `KE_VULKAN_PIPELINE_CACHE` relocates the cache or turns it off. `SetPipeline` emits `vkCmdBindPipeline` and then invalidates recorded descriptor slots from the first incompatible set onward, with a pipeline-identity guard in front that is strictly stronger than the layout one: two different programs sharing a layout each bind and invalidate nothing, and the same pipeline twice does neither. Creating a pipeline is UNREACHABLE from the recording type, which is the descriptor rule applied to the most expensive thing a driver does on demand, so a command list holds a separate one-call binder that can bind a pipeline that exists and can make none. It has a WINDOWED SWAPCHAIN too ([#527](https://github.com/APKiwiOrg/KhaozEngine/issues/527)), so `GpuDeviceContext.CreateForWindow` reaches a real native device: one platform surface chosen from `GpuWindowKind`, candidates filtered on whether their graphics family can present to it, `VK_KHR_swapchain` on the device, and a swapchain the present boundary acquires from, resizes, recreates and presents, behind an `IGpuDevice.SwapchainFramebuffer` whose identity never changes while every image view underneath it is replaced. Not one line of that path runs in CI on any leg, ever, because a headless Vulkan device enables no surface extension at all, which is what shaped the row: the create-info is decided in a pure function and the whole present boundary sits above a two-interface seam, so the format, the present-mode ladder, the image count, the extent clamp, the retry count, the retirement order and the counter are asserted device-free while a human at a window is the only instrument for the rest. The create-info is REPRODUCED from the incumbent exactly (`B8G8R8A8_UNORM` in `SRGB_NONLINEAR`, `min(maxImageCount, minImageCount + 1)` images, `COLOR_ATTACHMENT | TRANSFER_DST`, `OPAQUE`, `clipped`, no MSAA and no depth), including `FIFO_RELAXED` under a vsync request, which permits tearing on a late frame and is arguably the wrong answer and is reproduced anyway because the pacing work ([#380](https://github.com/APKiwiOrg/KhaozEngine/issues/380)) is where that gets decided with a measurement. Two deliberate departures, both bugs rather than behaviours: `preTransform` reads the surface's `currentTransform` rather than being hardcoded to `IDENTITY`, and the incumbent's sRGB fallback compares an already-`Undefined` format against an sRGB one so its intended throw is dead code, where this one refuses for real. The one behaviour that CHANGES is forced rather than preferred: the incumbent blocks the CPU on a fence every frame and then presents with no wait semaphore at all, which is a specification violation a validation layer flags, and a design that gates on validation cannot deliberately reproduce a configuration validation rejects. So the acquire TIMING is kept and the SYNCHRONISATION is replaced, with `KE_VULKAN_ACQUIRE=stall` restoring the incumbent's shape exactly for the A/B, documented as not usable with the validation knob, and removed at rollout gate 4 with the blocking path deleted. The acquire semaphores are a ring indexed by a MONOTONIC ACQUIRE COUNTER and never by image index, which is the most common Vulkan swapchain bug and manifests as an intermittent hang rather than a clean failure, sized `max(FramesInFlight, imageCount) + 1` because acquires are paced by the presentation engine while recording is paced by the frame loop. The `OUT_OF_DATE` boundary is four questions answered in one method: the recreate runs at that SAME boundary so the failed acquire's semaphore is retired by its unconditional drain rather than reused or destroyed while pending, ONE fresh acquire follows before the boundary returns, the retry is ONE so a surface mid-resize cannot spin it, and an imageless frame binds a device-owned ORPHAN TARGET and then records, submits and completes exactly like any other frame with only its present skipped, which `FramesBegun` still counts. A minimised window is survivable by ARITHMETIC rather than by a special case: its surface reports every extent as zero, the clamp produces zero, and the spec then reads as not creatable, so `vkCreateSwapchainKHR` is never called at a size the specification forbids. A resize, a runtime `SyncToVerticalBlank` change and a checked `vkQueuePresentKHR` result all queue the same recreate, coalesced and applied at the next boundary on the submit thread, and Vulkan cannot change a present mode in place so vsync is a full recreate here rather than the argument of a present call it is on Direct3D 11. The new views are published onto the existing wrapper BEFORE the old ones are destroyed, every time, and a creation that fails at a creatable extent keeps the old generation and retries, because that is the only response with no window in which the wrapper names a dead view. **One seam member pair is added with it: `GpuDeviceCounters.AcquireWaitCount` and `AcquireWaitMs`, with the `gpuAcquireWaits` and `gpuAcquireWaitMs` channel names**, without which the acquire A/B has only mean frame time to read and both positions produce the same mean by construction on a machine pinned at its refresh rate. The native Direct3D 11 device passes zero for the pair, which is the honest reading on a backend whose present has no acquire to wait on. It has a BARRIER AND LAYOUT TRACKER too ([#524](https://github.com/APKiwiOrg/KhaozEngine/issues/524)): every image layout transition is a `vkCmdPipelineBarrier2` whose stage and access masks are answered per LAYOUT rather than per layout PAIR, so the pair space is total by construction and a layout it does not know throws by name, against an incumbent that runs a 25-arm if/else over pairs, ends it in a debug assertion, and in Release emits `NONE` on both stage masks for a pair it does not handle, which is a barrier that synchronises nothing on a path whose only signal compiles away. Tracking is per subresource RANGE and per COMMAND LIST, against the canonical resting layout each texture was assigned at creation: a list assumes every texture is at rest when it starts, transitions as it needs, and restores everything it touched before `End`, so nothing shared is read or written during recording, two lists cannot disagree, and their submissions compose in any order. The incumbent keeps that state ON the texture instead, so the loser of a two-recording race records either a redundant barrier or NO barrier for a transition it needed, which is a corruption no golden on a software rasterizer will show. **What the ruling LOSES is recorded rather than left to be discovered: `OpenListTrackingGpuDevice` passes TRIVIALLY on this leg**, exactly as it does on the Direct3D 11 native leg, so a reader must not take it as evidence about this backend. | **KhaozEngine.Server** | `Foundation` + netcode (`Netcode`/`.Abstractions`/`.LiteNetLib`) + `Simulation` (fixed-tick host) + `Replication` + `WorldStore` (the `IWorldStore` seam + `InMemoryWorldStore` only; the `.Sqlite` / `.SqlServer` durable backends are opt-in siblings, added explicitly, not bundled) + `Sharding` (cell grid) + `NetWorld` (authoritative movement server + client glue + `WorldPersistence`) + the `CodeHealth.Analyzers` file-size ratchet | a headless sim server (no GPU) |
| **KhaozEngine.Foundation** | the GPU-free foundation (Primitives/App/Content/Diagnostics/Ecs/Http/Identity/Locomotion/MapDoc/Dungeon/Navigation/Objectives/Persistence/Progression/Stats/Serialization/ServerStatus/Social/Collision/Physics/Terrain/Determinism/Platform/Updates) + the `CodeHealth.Analyzers` file-size ratchet | a gameplay-logic library (no renderer) |

`KhaozEngine.Commerce` is not in any umbrella; a game or server that wants the wallet adds it explicitly. Same as `WorldStore`, its `.Sqlite` / `.SqlServer` durable backends are opt-in siblings, not bundled anywhere (including `Server`).

Target framework `net10.0`, with two exceptions: `KhaozEngine.ServerStatus` and its dependency chain
(`KhaozEngine.Diagnostics`, `KhaozEngine.Primitives`), plus the dependency-free `KhaozEngine.Http`, also
multi-target `net8.0`, so a small status endpoint (or any other Azure Functions consumer that wants the
bounded HTTP retry) can run as an isolated-worker app on the Linux Consumption (Y1) plan, which supports .NET
8 but not .NET 10. Every other package stays `net10.0`-only. MonoGame-free: Silk.NET windowing/input (GLFW
natives bundled per-RID), Veldrid behind `KhaozEngine.Gpu` for the GPU, Silk.NET.OpenAL for audio.
`System.Numerics` math throughout.

## Why it exists

KhaozEngine began as a shared input + screen-stack foundation extracted from three MonoGame games (a
Rule-of-Three extraction), with one improvement: the raw hardware read sits behind a seam so the whole
input + routing surface is **unit-testable without a device**. It then grew into a full custom stack and the
games migrated **off MonoGame entirely** - MonoGame's GLSL-1.20-on-Apple dead end forced a custom Veldrid/Metal
renderer, and once 2D, 3D, text, audio, and input were all proven on the custom stack the legacy MonoGame
packages were deleted. The headline payoff is unchanged: the **click-through fix** (a tap only registers when
press-origin and release land in the same target, and overlays reserve their footprint so clicks never leak to
the layer beneath) lives in one place. See [`docs/CROSS-PLATFORM.md`](docs/CROSS-PLATFORM.md) for the per-OS GPU story.

## The one rule that matters most

> **`AppWindow` is the only code in the entire stack that touches the Silk.NET/GLFW input.** Everything above it
> reads an immutable `InputState` snapshot (handed in each frame via `Frame.Input`) through `InputManager` /
> `Pointer`. Games must not reach around the seam - doing so re-introduces the untestable, click-through-leaking
> pattern this library exists to kill. And hit-test with the bounds helpers (`IsTapIn`, …), never raw
> position + button.

Full consumer contract: [`docs/USING-KHAOZENGINE.md`](docs/USING-KHAOZENGINE.md). Read it before wiring a game in.
All docs are indexed in [`docs/INDEX.md`](docs/INDEX.md) (living docs vs the dated design archive).

## Quickstart (the canonical game-loop wiring)

A game subclasses `GameApp` (2D) or `GameApp3D` (3D) and overrides the per-frame seams; the base owns the
`AppWindow.Run` loop, clock, viewport, input, and the 2D batch. The smallest thing that runs:

```csharp
using KhaozEngine.Game;
using KhaozEngine.Render2D;
using KhaozEngine.Windowing;

public sealed class MyGame : GameApp
{
    public MyGame() : base(GameAppOptions.For("My Game", 1280, 720)) { }

    protected override void OnUpdate(float dt) { if (Input.WasPressed(Key.Escape)) Quit(); }
    protected override void OnDraw2D(SpriteBatch batch) { /* batch.Draw(...) / DrawString(...) */ }
}

// Program.cs
using var game = new MyGame();
game.Run();
```

Full wiring reference (the 3D `OnDraw3D`/`GameApp3D` pass, scenes, input, fonts, the click-through-safe
`Pointer.IsTapIn` pattern): [`docs/USING-KHAOZENGINE.md`](docs/USING-KHAOZENGINE.md), "Wiring a game".

## Consuming the packages

Published to GitHub Packages on tagged releases, and packed to a local file-feed for day-to-day development.
The repo is public, so the Packages feed needs no authentication to restore from.

```xml
<!-- nuget.config (additive) -->
<add key="khaozengine-local" value="~/KhaozEngine/local-feed" />
<!-- or the GitHub Packages feed (public, no PAT needed):
     https://nuget.pkg.github.com/APKiwiOrg/index.json -->
```
```xml
<!-- One reference per project via an umbrella metapackage. Pick the bundle that fits: -->
<PackageReference Include="KhaozEngine.Game2D"     Version="17.35.0" />  <!-- desktop 2D: 2D runtime + GameApp/SceneManager + foundation -->
<PackageReference Include="KhaozEngine.Game3D"     Version="17.35.0" />  <!-- desktop 3D: Game2D + Render3D + the 3D scene bridge -->
<PackageReference Include="KhaozEngine.Server"     Version="17.35.0" />  <!-- headless: foundation + netcode, no graphics -->
<PackageReference Include="KhaozEngine.Foundation" Version="17.35.0" />  <!-- gameplay-logic lib: foundation only, no renderer/netcode -->
```

The metapackages have no code; they just pull in the granular packages. You can still reference those
directly (e.g. just `KhaozEngine.Netcode.Abstractions` for a wire-contract project) and mix a bundle with extra
packages (e.g. `KhaozEngine.Game2D` + `KhaozEngine.Netcode.LiteNetLib` for a 2D multiplayer game).

**Versioning is SemVer.** Each game pins a version and adopts fixes by bumping it - so you can keep one game on an old version while you migrate another. Don't fork the packages; if a game needs an API that isn't there, add it here and bump the version.

## Testability standard

Every input and routing path is covered by headless xUnit tests (split per area, e.g. `KhaozEngine.Render.Tests`
for `Windowing`/`InputManager`), by constructing `InputState` snapshots frame-by-frame and feeding them to
`InputManager.Update` (`dt` is a plain `float` in seconds). New behaviour ships with a headless test in its
matching per-area project, or the rump `KhaozEngine.Tests` when genuinely cross-cutting. This is the standard,
not a nicety - it's the reason the raw read sits behind the `AppWindow`/`InputState` seam.

```bash
dotnet test
```

**Windowed smoke (CI / quick check).** Every windowed sample honors `KE_MAX_FRAMES=N`: render N frames, then
exit 0. So any of them doubles as a smoke test on a GPU box without needing someone to close the window:

```bash
KE_MAX_FRAMES=5 dotnet run --project KhaozEngine.Showcase
# to smoke a specific room's world build, auto-enter it (case-insensitive prefix of the room title):
KE_SHOWCASE_ROOM="3D" KE_MAX_FRAMES=5 dotnet run --project KhaozEngine.Showcase
```

**Field capture (measuring a backend).** The Showcase also carries the levers a windowed performance capture
needs. They are the testbed's own, not engine API, and each is a no-op unless set:

| Variable | What it does |
|---|---|
| `KE_TELEMETRY_PATH=<file>` | Arms the engine's `TelemetryRecorder` for the whole run: a JSON Lines session with the engine's header (build, backend, adapter, every `KE_` lever) and a raw sample row every 100 ms carrying frame rate, frame times, a loop frame count and the `GpuDeviceCounters` channels |
| `KE_SHOWCASE_FRAME_CAP=auto\|uncapped\|<hz>` | Pins the frame-cap intent. The default `auto` resolves to a SOFTWARE cap on Metal plus vsync, which sleeps the loop before the present can block, so an acquire-wait or present-pacing reading has to be taken `uncapped` |
| `KE_SHOWCASE_BACKGROUND_THROTTLE=off` | Disables the unfocused/minimized pacing. The engine default caps an unfocused window at 15 Hz, which is right for a game and ruinous for an unattended capture that never takes focus |

```bash
# a bounded capture of the 3D room on a named backend, paced by nothing but the present
KE_TELEMETRY_PATH=/tmp/ke-capture.jsonl KE_GRAPHICS_BACKEND=metal-native \
KE_SHOWCASE_ROOM=3D KE_SHOWCASE_FRAME_CAP=uncapped KE_SHOWCASE_BACKGROUND_THROTTLE=off \
KE_MAX_FRAMES=8000 dotnet run --project KhaozEngine.Showcase -c Release
```

## Dev tools

Author-time dotnet tools that ship as packages on the shared version line (not runtime dependencies):

- **`ke-sfxbake`** (`KhaozEngine.Sfx.Tool`) - manifest-driven bulk SFX generation + bake. Each game owns a
  `sfx.manifest.jsonc` describing its effects; the tool generates them via the ElevenLabs sound-effects API and
  encodes into the asset tree, skipping anything already up to date (`.sfxmeta` hash sidecars). Needs
  `ELEVENLABS_API_KEY`, plus an ffmpeg with libvorbis or `oggenc` (vorbis-tools) for OGG output.

  ```bash
  export ELEVENLABS_API_KEY=...           # already set on dev machines
  ke-sfxbake bake path/to/sfx.manifest.jsonc --dry-run   # plan + estimated credits, spends nothing
  ke-sfxbake bake path/to/sfx.manifest.jsonc             # generate new/changed, skip unchanged
  ke-sfxbake bake path/to/sfx.manifest.jsonc --force     # regenerate everything
  ```

  ```jsonc
  // sfx.manifest.jsonc - paths resolve relative to this file
  {
    "sounds": [
      { "key": "ui/confirm", "prompt": "crisp sci-fi UI confirm blip, short synth tail",
        "durationSeconds": 1.2, "out": "Assets/Sfx/ui/confirm.ogg" },          // mono OGG (default)
      { "key": "ui/click", "prompt": "soft latency click", "format": "wav",
        "out": "Assets/Sfx/ui/click.wav" },                                     // 16-bit PCM WAV for one-shots
    ],
  }
  ```

- **`ke-updater`** (`KhaozEngine.Updates.Tool`) - generate, sign, and verify update manifests (RSA-2048).
