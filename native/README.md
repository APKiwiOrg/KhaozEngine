# KhaozEngine native core spike

The C++20 shared library exposes its C ABI in [khaoz_native.h](include/khaoz/khaoz_native.h). Check
the ABI version after loading the library. Any addition, removal or change to a public export
increments the version. The error accessor reports the calling thread's last
recorded exception and accepts a null buffer to query the length. If recording a diagnostic runs
out of memory, the accessor reports a fallback message to the calling thread. A thread that has yet
to record an error reads an empty message.

POSIX builds store full diagnostics in checked pthread slots. Linux places its one-byte fallback
flag in the module's static TLS block at library load. A loader with exhausted static TLS can
refuse that load.
On macOS, a preallocated table tracks fallback owners by native thread ID if pthread refuses the
fallback slot. It reuses records of exited threads and holds up to 1,024 simultaneous owners. If it
fills, the guard still returns its result code.

Published POSIX keys stay reserved until process exit, so libc can finish thread cleanup safely
after an explicit library unload.
On glibc, throwing any C++ exception allocates the runtime's own exception storage before the
guard's catch runs. A thread that cannot allocate that storage aborts, as in any C++ library, so
the result code covers every failure after the throw and not an out-of-memory throw itself.

## Prerequisites

Use CMake 3.28 or later, Ninja and a toolchain with C and C++20 support. Use Apple Clang on macOS, GCC or Clang
on Linux, and MSVC from an x64 developer shell on Windows. The macOS preset targets macOS 15.0
or later. All dependencies are in [third_party](third_party/README.md), so configure, build and
test work offline. If you previously configured the preset with another toolchain, configure
once with `cmake --fresh --preset <name>` to clear the cached toolchain.

Run the commands for your platform from this directory. On the shared development Mac, run
configure, build and CTest through build-slot with a label for each command.

### macOS arm64

    cmake --preset macos-arm64
    cmake --build --preset macos-arm64
    ctest --preset macos-arm64

### Linux x64

    cmake --preset linux-x64
    cmake --build --preset linux-x64
    ctest --preset linux-x64

### Linux arm64

    cmake --preset linux-arm64
    cmake --build --preset linux-arm64
    ctest --preset linux-arm64

### Linux x64 with address and undefined behavior sanitizers

    cmake --preset linux-x64-asan
    cmake --build --preset linux-x64-asan
    ctest --preset linux-x64-asan

### Windows x64

    cmake --preset windows-x64
    cmake --build --preset windows-x64
    ctest --preset windows-x64

Each preset writes the build and compilation database under out/build in this directory.
Build presets pass `-k 0` to Ninja, so one build reports every compile error.
Release builds carry debug information. MSVC links it into a separate PDB. CI splits it into a
symbols artifact and strips the shipped library. Shipped Linux libraries are built inside the
`manylinux_2_28` images, so they need glibc 2.28 at most. The shipped Linux library links libstdc++
and libgcc statically. Tests and fixtures use the shared runtime, since a fixture with its own static
copy allocates an exception pool at load that unloading never frees.

## Source checks

Use LLVM's clang-format and run-clang-tidy from this directory. The formatter checks tracked
files and new files that Git does not ignore, excluding `third_party/`. The linter checks
first-party translation units from the configured preset's compilation database and reports
diagnostics in their non-system headers. Include vendored headers by name in angle brackets
through the `khaoz::*` targets, which supply their SYSTEM include paths. The include check uses
preprocessor output to flag vendored headers opened as non-system headers. It accepts compilation
databases generated by this repository's CMake presets for Clang or GCC with GNU-style options.
It forwards recognized preprocessing options, including the `-fsanitize=` and `-fno-sanitize=`
families, keeps output in a private temporary directory, and refuses response files, compiler
configuration options and compiler pass-through arguments. For each distinct flag set it first
dumps the macros an empty source predefines, once with the compile command's own options minus its
source, output and dependency options, and once with the forwarded options. Any difference fails
the check, so dropping an option that changes a macro cannot hide an include.

```sh
preset=macos-arm64
build_dir="out/build/$preset"
cmake --preset "$preset"

git ls-files -z --cached --others --exclude-standard -- \
  '*.[cChH]' '*.cc' '*.cp' '*.cpp' '*.cxx' '*.c++' '*.hh' '*.hpp' '*.hxx' '*.h++' \
  '*.inc' '*.inl' '*.ipp' '*.tcc' '*.tpp' '*.ccm' '*.cppm' '*.cxxm' '*.c++m' '*.ixx' \
  ':(exclude)third_party/**' | xargs -0 clang-format --dry-run --Werror --

python3 scripts/check-vendored-includes.py -p "$build_dir"

native_root=$(python3 -c 'import os, re; print(re.escape(os.getcwd()))')
run-clang-tidy -quiet -j 1 -config-file="$PWD/.clang-tidy" -p "$build_dir" \
  -source-filter "^${native_root}"'[/\\](?!third_party[/\\])'

scripts/refresh-third-party.sh --check
```

## Headless Vulkan transfer subset

The C ABI can probe for and create a headless Vulkan 1.3 device. The default creation function
reads `KHAOZ_NATIVE_VULKAN_LOADER`. The explicit loader function accepts a path from callers
that manage their own environment. The selector entry point passes adapter metadata in
enumeration order to its callback, then uses that same enumeration to open the chosen
device. It checks driver availability and adapter eligibility without layers before creating a
validation-enabled instance. A failure to open the unlayered instance or enumerate an eligible
adapter reports machine unavailability. Startup status identifies a missing driver, including
an instance that enumerates no devices. Devices use per-instance and per-device dispatch tables.
Portability enumeration and the portability subset are enabled when exposed. The sampler uses
zero mip LOD bias when the portability subset is enabled, since the spike does not enable
the optional portability feature for sampler bias. The capability reports the bias mode
used to create samplers.

Buffers and images are allocated through VMA. Staging textures use host-visible buffers with
a layout for each mip and array layer. A logical cubemap layer allocates six faces, and
transfer indices address those physical faces. Off-timeline uploads wait for completion. Transfer
lists submit asynchronously and can signal a fence. Images rest in `GENERAL` so abandoning or
reordering lists leaves their layout valid. Release children before destroying the device and
serialize calls on each device. Validation catches a device closed with live children and the
ABI returns the total count after releasing the children, the device and the instance.
An inconclusive queue wait refuses new work and retains submitted resources until a later
wait drains the queue or the device is destroyed.
A device destroy that cannot confirm either queue completion or device loss retains the
handle for a later retry.

Set `KHAOZ_NATIVE_GPU_TESTS=1` to run the GPU doctests. These require an available Vulkan device
and `VK_LAYER_KHRONOS_validation`. On macOS use the MoltenVK ICD and expose the validation
layer manifest and its library to the Vulkan loader.

## Headless Vulkan graphics subset

A graphics shader set takes vertex and fragment SPIR-V with entry point `main`. The managed
adapter generates both modules with the shared GLSL front end. Layout positions are descriptor
binding numbers, and pipeline layout positions are set numbers. Sampled images and samplers use
separate bindings. Uniform descriptors are dynamic, with offsets composed in binding order.
The buffer window contributes its base offset and a declared-dynamic element also takes the
caller's offset. The spike records uniform uploads into the command list using staging buffers.

Framebuffers use the first mip and array layer of each attachment and require matching extents
and sample counts. Binding one copies its attachment description into the command list. A bound
resource set is recorded as a shared immutable copy of what draws check, so a draw never reads a
destroyed set. The command list starts Vulkan dynamic rendering on the first draw or when
a queued clear needs to be flushed. Image views use the images' `GENERAL` layout. The viewport
uses negative height and the scissor uses top-left framebuffer coordinates, matching the managed
Vulkan backend. Recorded copies and buffer uploads close the rendering scope so transfers can
run between draws. Reopening the scope loads the previous attachment contents. Texture copies
require the same native Vulkan format and aspects on both sides. An R32Float depth texture is
`D32_SFLOAT` and an R32Float colour texture is `R32_SFLOAT`, so copies between them are refused.
Staging textures are colour, so a depth texture cannot be read back through one.

Destruction follows the managed backend's deferred model. Destroying a texture, buffer, sampler,
resource set, pipeline or framebuffer waits for submitted work, then deletes it only when nothing
still holds it. A command list holds every pipeline, framebuffer, resource set, buffer and texture
it records, until the list begins again, is destroyed, or a drained queue proves its submitted
work finished. A framebuffer holds its attachment textures and a resource set holds the buffers,
textures and samplers its descriptors name. So an object destroyed while an open recording uses
it stays valid through End and Submit. The device deletes released objects nothing holds after a
successful queue wait, after each destroy, at the next Begin and at device teardown.

## Package and smoke test

[KhaozEngine.Native.csproj](KhaozEngine.Native.csproj) packs prebuilt libraries into
`KhaozEngine.Native`. It compiles no source and globs nothing. It sits at the root of `native/`, so
Product CI's scope row for it covers the C++ sources and a C++ change selects the native core
workflow without a full scope. Pass `KhaozNativeStage`, a folder with one subfolder per
RID: `osx-arm64/libkhaoz_native.dylib`, `win-x64/khaoz_native.dll`, `linux-x64/libkhaoz_native.so`
and `linux-arm64/libkhaoz_native.so`. Each present library lands in `runtimes/<rid>/native/`, so a
partial stage packs only those RIDs and a build without a stage still compiles. Stage stripped
libraries, since game repositories vendor every engine version into git.
[scripts/stage-library.sh](scripts/stage-library.sh) copies a preset's build into that layout under
`<out>/lib`, with its debug information under `<out>/symbols` and the test fixture libraries under
`<out>/fixtures`. The fixtures never go in the package. The spike packs only to a run-local folder, never to
`local-feed`.

[smoke/NativeSmoke.csproj](smoke/NativeSmoke.csproj) consumes the package as a game would. It links
the generated bindings and `NativeLibraryGate.cs` from `KhaozEngine.Gpu.Core`. It exits 0 only when
the gate reports `Ready`, a 3,335-record frame returns its keys sorted, and headless device creation
either succeeds and destroys with zero validation errors or reports `KHAOZ_ERROR_VULKAN_UNAVAILABLE`.
Validation follows `KHAOZ_NATIVE_VALIDATION=1`, since it needs the Khronos layer. The CI smoke legs
run without the layer, so a smoke pass shows the package loads and works, not that it validates
cleanly. Validation runs in `Test: native-golden` and `Test: native-asan` on lavapipe. The
[nuget.config](smoke/nuget.config) beside it restores `KhaozEngine.Native` from the folder in
`KHAOZ_NATIVE_FEED`. Without `KhaozNativeVersion` the project compiles with no package, which is how
Product CI builds it.

From the repository root, after building the macOS preset:

```sh
work=/tmp/khaozengine-native
sh native/scripts/stage-library.sh native/out/build/macos-arm64 osx-arm64 "$work/stage"
dotnet pack native/KhaozEngine.Native.csproj -c Release \
  -p:KhaozNativeStage="$work/stage/lib" -p:Version=0.0.0-spike.0 -o "$work/feed"
KHAOZ_NATIVE_FEED="$work/feed" NUGET_PACKAGES="$work/packages" \
  dotnet run --project native/smoke/NativeSmoke.csproj -c Release -p:KhaozNativeVersion=0.0.0-spike.0
```

The `native-core-spike` workflow builds every RID, packs all four and runs the smoke app on each
hosted platform and inside the `mcr.microsoft.com/dotnet/sdk:10.0` image on Linux arm64. Its Scope
job selects it through the Product CI rules, and it owns the device tests in
`KhaozEngine.Gpu.Core.Tests`, which skip on the GPU workflow's legs without the native library.
